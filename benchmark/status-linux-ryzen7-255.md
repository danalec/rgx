# rgx: Status & Benchmark Dashboard — Linux (Ryzen 7 255)

Measured numbers on a **second machine**, saved alongside — not instead of —
the Windows dashboard in [`status.md`](status.md). Same harness, same gated
protocol, same digest-pinned corpora. The point of this file is the
cross-machine picture: which ratios travel and which are the host's.

- **Machine:** AMD Ryzen 7 255 w/ Radeon 780M (10 logical CPUs visible),
  15 GiB RAM, CachyOS (Linux 7.2.7-1-cachyos), `rustc 1.98.1`. Default
  portable release build — `cargo build --release`, no `RUSTFLAGS`. This is
  a mobile-class Zen 4 APU, not the 7950X3D the Windows table was taken on.
- **Reference:** `ripgrep 15.2.0` (the Windows table used 15.0.0).
- **Harness:** `cargo run --release -p rgx-core --example status_table`
  (`scripts/bench-status.sh` wraps it) — 7 timed rounds per cell, 2 discarded
  warmups, minimum reported, ±3% floor, `-c` count gate in front of every
  timing line, engines interleaved inside every round with the order
  alternating. **All 22 rows passed the gate.**
- **Corpora, named by digest.** Generated by `scripts/make-corpus.py` with
  the same seed as the Windows run:
  - one file: `big235.rs`, 246,541,116 bytes,
    `9c38d37f2f578287cb9c7731b0dabeafe38e2d629b04cbbbc3d14596de6c0ab8`
    — **byte-identical to the Windows corpus.** Directly comparable.
  - many files: the generated tree, 20,000 files / 417.7 MB,
    `420ca0a1d6a865ec63e19396f46063f019856ea567ca5a3f0f1784481e1655a1`
    — same generator and seed; the Windows snap's digest differs because
    that tree carried 28 leftover store files of a previous generation
    (20,028 walked entries). The 20,000 generated files are the same bytes.
  - this repository (working tree; digest moves with the tree).
- **Threads:** `-j1` on the single-file rows (engine alone), `-j10` on the
  directory rows — thread-matched, the same N to both engines.

## 1. Three corpora, three questions

### 1.1 One file — the engine alone, no walk
`big235.rs`, 246,541,116 bytes, `-j1`, thread-matched, no filter.

| pattern | lines rgx / rg | rgx | ripgrep | ratio | verdict |
|---|---:|---:|---:|---:|---|
| `e` | 6,941,931 / 6,941,931 | 165.6 ms | 231.0 ms | **1.39x** | rgx **+39.5%** |
| `e.` | 6,927,072 / 6,927,072 | 314.6 ms | 310.7 ms | 0.99x | tie (inside ±3%) |
| `foo.*bar` | 264,029 / 264,029 | 93.6 ms | 61.4 ms | **0.66x** | ripgrep **−34.4%** |
| `pub fn` | 882,393 / 882,393 | 113.1 ms | 71.2 ms | **0.63x** | ripgrep **−37.1%** |
| `e[0-9]` | 240,786 / 240,786 | 93.4 ms | 55.2 ms | **0.59x** | ripgrep **−40.9%** |
| `(pub\|fn) [a-z]+` | 1,236,465 / 1,236,465 | 167.8 ms | 142.9 ms | **0.85x** | ripgrep **−14.8%** |
| `a\|b\|c` | 6,019,540 / 6,019,540 | 183.8 ms | 219.7 ms | **1.20x** | rgx **+19.6%** |
| `fn main` | 175,860 / 175,860 | 75.8 ms | 42.5 ms | **0.56x** | ripgrep **−43.9%** |
| `let mut` | 39,795 / 39,795 | 71.4 ms | 41.0 ms | **0.57x** | ripgrep **−42.6%** |

All nine gates PASS and all nine rows separate. **The split is by pattern
shape, not by noise.**

**This is the row set where the two machines disagree, and the disagreement is
structured.** The Windows 7950X3D table (same corpus, same digest) has rgx
ahead on **all nine**, +33.1% to +113.6%. Here rgx is ahead on the two
**single-byte** shapes (`e`, `a|b|c`), ties `e.`, and **loses the six
multi-byte / class shapes** by 14.8% to 43.9%. The pattern is consistent with
the two engines' prefilter strategies: ripgrep's packed-pair literal kernel
is strong when the needle has two rare bytes to test (`pub fn`, `fn main`,
`let mut`), and rgx's in-house engine is strong when the scan is dominated by
a single high-frequency byte whose candidates the mask rectifies in-register
(`e`, `a|b|c`). What travels across machines is the *shape dependence*, not
the sign of the headline.

**Consequence for any claim of engine superiority: it must name the host.**
The Windows table's "rgx +33% to +114% on nine pattern shapes" is true of
that machine and false of this one. The ratios are not a property of the
code alone.

| `(pub\|fn) [a-z]+` | 2,091,372 / 2,091,372 | 104.3 ms | 99.9 ms | **0.96x** | ripgrep **−4.2%** |
| `a\|b\|c` | 10,201,075 / 10,201,075 | 112.9 ms | 105.1 ms | 0.93x | **overlap, not a result** (−6.9%) |
| `fn main` | 297,851 / 297,851 | 85.7 ms | 73.5 ms | **0.86x** | ripgrep **−14.3%** |
| `let mut` | 67,616 / 67,616 | 82.4 ms | 73.5 ms | **0.89x** | ripgrep **−10.7%** |
| `walk (--files)` | 20,000 / 20,000 | 9.4 ms | 6.6 ms | **0.70x** | ripgrep **−29.8%** |

**Ripgrep leads or ties every row here.** On the Windows host the same
corpus gave rgx a +5.7% to +8.6% edge on the search rows and +60.7% on
`--files`. The walk-dominated conclusion survives in one direction only: a
perfect matcher cannot buy much on this corpus (the engine share is small),
but *which* tool is ahead on the walk itself is host-dependent. This host
favours ripgrep's walker by ~30%.

The honest summary of §1.2 across both machines: **on a walk-dominated
corpus of 20k small files the two tools are within ~±15% of each other on
every search shape, and the sign of the edge is a property of the host.**
Neither machine shows a large engine-driven win on this corpus, which is the
scale-separation claim the paper makes — but the project's previous
statement that "no row is a ripgrep win" is a fact about the Windows snap
and not a portable one.

### 1.3 This repository
`crates/` + `src/`, `-j10`, pattern `fn main`, plus the asymmetric archive row.

| row | lines rgx / rg | rgx | ripgrep | ratio | verdict |
|---|---:|---:|---:|---:|---|
| `crates` | 47 / 47 | 9.1 ms | 4.6 ms | **0.50x** | ripgrep **−49.5%** |
| `src` | 3 / 3 | 3.9 ms | 3.0 ms | **0.76x** | ripgrep **−24.2%** |
| `archive-extract` | 20 / 9 (+11 in archives) | 605.5 ms | 5.8 ms | n/a | rgx **+11 hits (+122% more)** |

As on Windows, the `crates`/`src` rows are per-walker fixed cost (47 and 3
lines cannot measure a matcher), and the asymmetric archive row is the one
with content: rgx reads inside RAR / 7z / tar.* / brotli / zstd / lz4 / xz /
lzma fixtures and returns 20 paths where ripgrep returns 9. The gate flips
to `rgx >= rg` and names the surplus. The 605 ms is the cost of work
ripgrep does not attempt.

## 2. Pack store on this host (three-arm A/B/C)

Paired protocol from [`tv-transcript.md`](tv-transcript.md): count gate
first, arms paired inside each round, order rotated, 7 rounds, minimum
reported, floor ±3%. Store built from the same generated tree:
**26 packs, 20,000 files, 417.73 MB, build 998 ms** (Windows: 2.26 s).
Threads: 10 (all arms).

| pattern | matches | rg | rgx | tv | vs rg | vs direct |
|---|---:|---:|---:|---:|---:|---:|
| `a\|b\|c` | 10,201,075 | 99 ms | 101 ms | **48 ms** | **2.06x** | 2.10x |
| `e` | 11,764,155 | 102 ms | 100 ms | **44 ms** | **2.32x** | 2.27x |
| `e.` | 11,739,023 | 118 ms | 133 ms | **76 ms** | **1.55x** | 1.75x |
| `pub fn` | 1,492,934 | 78 ms | 90 ms | **34 ms** | **2.29x** | 2.65x |
| `fn main` | 297,851 | 67 ms | 81 ms | **26 ms** | **2.58x** | 3.12x |
| `let mut` | 67,616 | 72 ms | 83 ms | **23 ms** | **3.13x** | 3.61x |
| `e[0-9]` | 406,122 | 73 ms | 85 ms | **29 ms** | **2.52x** | 2.93x |
| `(pub\|fn) [a-z]+` | 2,091,372 | 90 ms | 99 ms | **45 ms** | **2.00x** | 2.20x |

Counts identical on every row — GATE PASS. Range against ripgrep
**1.55x–3.13x**; against direct rgx **1.75x–3.61x**. Mean query cost (means of the minima above):
rg 87.4 ms, rgx 96.5 ms, tv 40.6 ms → break-even **Q\* ≈ 21** vs ripgrep,
**≈ 18** vs direct (T_build = 998 ms).

**What this confirms and what it does not.** The architecture's claim —
that a prepared store removes the $\mathcal{O}(N)$ term and answers faster
than either direct path — holds on a second OS, a second CPU class, and a
second thread count. Every arm returned exact count parity. What it does
*not* confirm is a portable headline multiplier: the Windows run quoted
2.79x–3.38x vs rg, this run gives 1.55x–3.13x. The low end moved a full
point (`e.` 2.79x → 1.55x). Compare runs by their reference-arm placement,
as [`tv-transcript.md`](tv-transcript.md) already warns.

## 3. Read mode on this host (mmap vs ParallelBuffered)

A paired, order-rotated probe of the three `rgx-tv search` read modes over
the same 26-pack store, pattern `fn main`, `-j10`, 7 rounds. This is the
question [`optimal-techniques.md`](optimal-techniques.md) claims a −44.3%
mean for `ParallelBuffered` over mmap on a Windows corpus that no digest
pins.

| mode | samples (ms) | min | paired vs mmap |
|---|---|---:|---|
| `--no-mmap` (ParallelBuffered) | 27, 27, 27, 28, 31, 33, 28 | **27** | — |
| `--mmap` | 31, 31, 31, 32, 32, 39, 31 | 31 | mmap slower on every round |
| `--serial-buffered` | 211, 213, 214, 224, 227, 254, 305 | 211 | ~8x slower than ParallelBuffered |

ParallelBuffered is faster than mmap on **every** paired round, by 3% to
18% (mean ≈ 12%), and serial-buffered is in a different regime entirely
(one pack at a time, no worker parallelism). **The direction of the
`optimal-techniques.md` claim reproduces; the magnitude does not.** −44.3%
is not observed here; the effect is a solid ~12%. The older figure is now
not merely unpinned — it is **contradicted in magnitude by a second host**,
while its direction (buffered beats mmap on a one-shot query) stands.

## 4. N-gram signature filter on this host

`crates/rgx-core/examples/diodicity.rs`, 15,000 files from the live Cargo
registry (315.27 MB). Latency is per file evaluated. Prune efficiency is
the percentage of files eliminated before a slice is borrowed.

| pattern | 256-bit prune | 512-bit prune | 512 latency | FN |
|---|---:|---:|---:|---:|
| `fn main` | 15.16% (2,274) | **28.61%** (4,291) | 3.61 ns/file | 0 |
| `pub fn` | 11.13% (1,669) | **22.92%** (3,438) | 3.43 ns/file | 0 |
| `let mut` | 14.34% (2,151) | **27.07%** (4,060) | 3.52 ns/file | 0 |
| `struct ` | 9.87% (1,481) | **21.37%** (3,205) | 3.48 ns/file | 0 |

Zero false negatives on every row. **512-bit prunes strictly more files
than 256-bit on every pattern** — the direction the idealised Bloom model
predicts.

### Root cause of the paper's "512-bit inversion": a column mislabel

The paper's original table reported 512-bit "admitting" 25–30% against
256-bit's 14–17%, which contradicts the Bloom model and was filed as an
open doubt. **There was no inversion.** The harness prints three columns —
files admitted, files pruned, prune efficiency — and the paper's table
copied the **pruned** count and the **prune efficiency** percentage into a
column it labelled "admitted".

Evidence, the `fn main` 256-bit row:

| source | count | percent | what it actually was |
|---|---:|---:|---|
| paper's "admitted" | 2,275 | 15.17% | **pruned** files, prune efficiency |
| this run's pruned | 2,274 | 15.16% | pruned files, prune efficiency |

One count apart. Under the correct labels the paper's own Run A already
said 512-bit prunes more (27.78% vs 15.17% on `fn main`) — textbook
direction. The error manufactured a phenomenon and invited a mechanism
(weakly-avalanched half-selector) to explain a non-event. The lesson is
about reporting: a filter output has an admitted side and a pruned side;
they are complements; a table that does not name which one it is printing
can invert the finding without changing a measurement.

Residual, narrower gaps (stated, not load-bearing):

- **Absolute prune rates differ across runs on 3 of 4 patterns** (this
  run 9.9–15.2% vs the paper's 13.8–17.1% at 256-bit) because
  `collect_rs_files` takes the first 15,000 `.rs` files in `readdir`
  order, which is not stable across machines. The `fn main` row shows what
  the same subset looks like. A digest-named n-gram corpus would close
  this.
- **Latency differs by 4–6×** (2.3–3.6 ns/file here vs 14.2–19.0 in the
  paper) in the opposite direction to the hosts' relative speed — a timer-
  scope difference, not a filter difference (the filter is a fixed number
  of word ANDs per file in both).

## 5. What this run settles, and what it does not

| doubt | status after this run |
|---|---|
| Engine-alone ratios are portable | **Refuted.** Same corpus, two hosts, opposite signs on 6 of 9 shapes. |
| Pack-store architecture works beyond one machine | **Confirmed.** Exact parity, 1.55x–3.13x over rg, Q\* ≈ 21. |
| `ParallelBuffered` is faster than mmap (direction) | **Confirmed** on every paired round. |
| `ParallelBuffered` is −44.3% faster (magnitude) | **Not reproduced.** ≈12% here. The older figure stays withdrawn. |
| 512-bit signature is weaker than 256-bit | **Closed: reporting error, not a finding.** The paper's "inversion" was the prune column mislabeled as admitted. Both runs show 512-bit pruning more, textbook direction, zero FN. |
| Walk-dominated corpora are close | **Confirmed in both directions** — but the sign of "close" is host-dependent. |

**Still open.** The absolute n-gram prune rates are not cross-host
comparable until the 15,000-file subset is digest-named (the harness
walks in `readdir` order). That is a corpus-stability gap of the same kind
`scripts/make-corpus.py` already closed for the dashboard — it does not
touch the ordering of the two widths, which is the question the doubt was
about.
